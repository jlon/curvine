## 性能分析

### 1. 延迟分析

**4K 随机读延迟分布：**
- P50: 235 μs
- P90: 474 μs
- P99: 938 μs
- P99.9: 1467 μs

**关键发现：**
- 平均延迟 286 μs 非常低
- 延迟分布集中（59.38% 在 250μs 以内）
- 说明锁竞争已经很小

### 2. CPU 使用率分析

所有测试的 CPU 使用率都很低（< 3%），说明：
- 不是 CPU 密集型瓶颈
- 主要瓶颈在 IO 等待
- 单线程 psync 无法充分利用系统资源

### 3. 块大小影响

| 块大小 | 带宽 | 带宽/块大小比 |
|--------|------|--------------|
| 4K | 13.6 MiB/s | 3.4 |
| 64K | 96.0 MiB/s | 1.5 |
| 256K | 275 MiB/s | 1.07 |

**观察：**
- 块大小越大，带宽越高（符合预期）
- 256K 随机读接近顺序读的 42%（654 MiB/s）
- 说明随机读性能已经很不错

## 优化效果归因

### 优化 1：移除 AsyncChannel (+51%)
- 顺序读：352 → 533 MiB/s
- 随机读：估计从 5.6 → 8.5 MiB/s

### 优化 2：移除 NfsReader 内部 Mutex (+23% 顺序读, +60% 随机读)
- 顺序读：533 → 654 MiB/s (+23%)
- 随机读：8.5 → 13.6 MiB/s (+60%)

**为什么随机读提升更大？**
- 随机读对延迟更敏感
- 移除 Mutex 后，延迟从 3ms 降到 1.5ms（-50%）
- 更低的延迟 → 更高的 IOPS → 更高的带宽

## 当前瓶颈分析

### 1. ReaderPool 大小限制（已验证！）

**问题：**
- ReaderPool 固定 8 个 reader
- 当线程数 = 8 时，锁竞争最严重
- 延迟从 286μs 暴涨到 5893μs（20倍！）

**证据：**
- 4 线程：+34% 性能提升 ✅
- 8 线程：-60% 性能下降 ⚠️

**结论：**
- ReaderPool 大小是当前的主要瓶颈
- 需要动态调整或增加 reader 数量

### 2. 单线程 IO 深度限制
- 当前：iodepth=1, numjobs=1
- 每次只有 1 个 IO 请求在飞行中
- 无法充分利用网络和存储并发能力

### 3. 协议开销
- 每次 READ 需要：
  - XDR 解码请求
  - 文件句柄验证
  - 状态查询（可能有缓存）
  - 数据读取
  - XDR 编码响应
  - 数据拷贝（DataSlice → Vec<u8>）

### 4. 网络往返延迟
- 即使是本地回环（127.0.0.1），仍有网络栈开销
- 每次 READ 都需要一次网络往返
